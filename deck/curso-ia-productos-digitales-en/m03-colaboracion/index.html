CHAPTER 01

Version control

The life insurance of any digital project. And with AI, more than ever.

WHY GIT

Git is your time machine

Git saves a snapshot of the project at every important moment. If something breaks, you can go back to any earlier point in seconds.

With AI this is even more valuable: the agent makes big changes without asking. A previous commit lets you undo everything with a single command.

HOW IT WORKS

From your computer to GitHub

Git has four zones. Each command moves changes from one zone to the next. github.com — create your account if you don't have one yet.

Working Directory

Where you edit the files. Changes aren't tracked by Git yet.

Staging Area

The waiting room. You prepare what goes into the next commit with git add.

Local Repository

The history on your machine. Commits saved with git commit.

GitHub (Remote)

The cloud. Backup and deployment point. Uploaded with git push.

THE ESSENTIAL COMMANDS

4 commands you need to master

  • 01

    git init / git clone

    Create a new repo locally or clone an existing one from GitHub. It's always your starting point in any project.

  • 02

    git add + git commit

    A snapshot of the current state. Do this BEFORE asking the AI for a big change. It's your safety net: if something breaks, you come back here.

  • 03

    git push

    Upload commits to GitHub. A cloud backup and, if you have continuous deployment set up, the automatic trigger for a new release.

  • 04

    git checkout / git reset

    Go back to a previous version. The lifesaver when something breaks after a session with the AI. The difference between losing hours and losing seconds.

IN PRACTICE

Your first commit

# 1. Create the project folder and turn it into a Git repository
git init my-first-repo
cd my-first-repo

# 2. Add all files to the staging area
git add .

# 3. Create the first commit with a descriptive message
git commit -m "first commit of the project"

# 4. Connect to the remote repository on GitHub
git remote add origin https://github.com/your-username/my-first-repo.git

# 5. Push the first commit to the main branch
git push -u origin main

git init Creates a hidden .git/ folder that contains the entire version history. Without this folder, the directory isn't a repository.

git add . The dot selects all modified files. You can be more selective: git add src/app.js only adds that file.

git commit -m Saves the snapshot with a message explaining what's in that state. The more descriptive, the more useful it will be months later.

git push -u The -u flag links the local branch to the remote one. It's only needed the first time; after that, git push is enough.

ESSENTIAL FILES

The file that protects your secrets

.gitignore is a list of files and folders that Git should ignore completely. It will never include them in any commit.

Without this file, you could accidentally upload your API keys, access tokens, database passwords, or hundreds of megabytes of dependency folders to GitHub.

It's created at the root of the project and Git reads it automatically. The first thing the AI does when it initializes a project is generate this file.

Golden rule: if you don't want the world to see it, it goes in .gitignore. If it needs to travel with the project, it goes in the repo.

BRANCHES

Experiment without breaking anything

The main branch is the stable version of your project. Feature branches let you test changes without affecting main.

With AI, use branches to experiment: if Claude Code or Antigravity suggests a big refactor, do it in a new branch. If it works, you merge it. If not, you delete it with no consequences.

git checkout -b feature/my-experiment

This is the basic flow. In the next slide we'll see how to scale this to the full team standard.

GITFLOW · TEAM STANDARD

The full workflow for real projects

Gitflow is the standard used by most professional teams. It adds two permanent branches and clear rules for when to do each thing.

  • main — code in production. Only receives from release or hotfix.
  • develop — continuous integration. Features go here.
  • feature/* — new features branched from develop.
  • release/* — prepare a release. Goes from develop to main.
  • hotfix/* — urgent patches from main, merged back into develop.

COMMIT MESSAGES

Conventional Commits

Conventional Commits is a standard for writing commit messages with predictable structure and semantic meaning.

The format is: type: description. The type declares what kind of change it is. The description explains the what.

The AI can generate and maintain this style automatically. Just state it in CLAUDE.md: "use Conventional Commits in all messages".

Commit types
feat: new feature — bumps the minor version
fix: bug fix — bumps the patch version
docs: documentation only, no code changes
refactor: reorganization without changing behavior
test: adding or fixing tests
chore: maintenance tasks with no impact
Real examples:
feat: add Google login
fix: fix bug when emptying the cart
docs: update README with requirements

CHAPTER 03

Project organization

A well-structured project is like a well-organized kitchen: the AI finds the ingredients where it expects to find them.

STANDARD STRUCTURE

The anatomy of a well-organized project

Every file has a reason to exist. The AI expects to find each piece in its place to work more efficiently.

The most important file for the AI is CLAUDE.md (or its equivalent in Antigravity): it tells it who you are, what the project does, what conventions to follow, and what it should never do.

Antigravity uses an equivalent file (the name varies by agent, but the concept is the same). Every agent has its own way of receiving context, but they all need it.

The .claude/ folder contains specialized agents in agents/ and reusable skills in skills/. The Antigravity equivalent follows the same principle.

CONVENTIONS

The rules that make everything fit together

  • 01

    English names for files and folders

    Technical identifiers in English with hyphens: user-auth, api-client. Documentation in whatever language you prefer. AI works better with English names.

  • 02

    README.md always at the root

    The first thing anyone (or any AI) sees when they enter the project. Without a README, the project doesn't exist for the world.

  • 03

    .gitignore from the first commit

    node_modules/, .env, __pycache__/, *.log never get uploaded to GitHub. Set it up before making the first commit.

  • 04

    CHANGELOG.md for important decisions

    Record what you changed and why. The AI can maintain it automatically with the right prompt in CLAUDE.md.

CHAPTER 04

Documentation that works

You don't document for the past. You document for the AI that will work with you tomorrow.

THE README

Anatomy of a good README

The README is the contract between your project and the world. In 60 seconds, anyone (or any AI) should understand what it does and how to run it.

Name and description — One line that defines the project. If you can't summarize it in one line, the project is doing too much.

Installation — The shortest possible path to get someone up and running. Ideally a single command.

Usage — A real example. Not what the project could do; what it does right now, with a concrete example.

Technologies — The stack: what languages, frameworks, and services it uses. The AI needs this information to generate compatible code.

Contributing — The ground rules if someone wants to collaborate, or if you want to tell the AI how it should make its PRs.

ESSENTIAL FILE

What should never reach GitHub

# === SECRETS — NEVER upload API keys ===
.env
.env.local
.env.production

# === DEPENDENCIES (all languages) ===
node_modules/       # Node.js
__pycache__/        # Python bytecode
*.pyc               # Python compiled
vendor/             # PHP Composer
.gradle/  build/    # Java/Kotlin

# === BUILD (regenerated on every deploy) ===
dist/   .next/   .nuxt/   out/

# === OPERATING SYSTEM ===
.DS_Store   Thumbs.db

# === LOGS AND TEMP FILES ===
*.log   npm-debug.log*

The rule is universal. Every language generates dependency folders that weigh hundreds of MB and can be regenerated. They're never versioned.

.env If you upload this file to a public repo, your keys are exposed. GitHub scans for leaked keys and notifies the providers. The key gets revoked automatically.

.env.example This one IS versioned: it lists which variables the project needs, without the real values. It's the guide for the team.

gitignore.io Generates the .gitignore for your stack in seconds: type "node express docker" and there it is.

DAILY WORKFLOW WITH GIT + AI

The ritual you'll repeat every day

  • 01

    git pull — sync before you start

    Pull changes from the remote. Even if you work alone, it's a good habit to avoid conflicts.

  • 02

    git checkout -b feature/name — new branch

    Never work directly on main. The branch protects the stable code from the day's experiments.

  • 03

    Ask the agent for the feature — Claude or Antigravity

    With a well-documented README and CLAUDE.md, the agent generates higher-quality code because it has real context about the project.

  • 04

    Test manually — the validation is always yours

    The AI doesn't have your full business context. Check that the result is what you wanted before committing.

  • 05

    git add + commit + push

    A snapshot of the good state, a descriptive Conventional Commit message, and a push to the remote.

You can ask the agent to handle this entire flow: create the branch, make the commit, open the PR. It's a good idea to do it by hand at first to master repository control. After that, you decide how much you delegate.
