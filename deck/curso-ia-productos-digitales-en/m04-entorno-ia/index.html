CHAPTER 01

DevContainers

The same environment for everyone, always. A new person joins the team, zero hours of setup.

CONCEPT

Your project as a reproducible environment

VS Code reads it and spins up the environment in seconds. Anyone who clones your repo gets exactly the same environment you have.

A DevContainer is a Docker container that defines your project's complete development environment: operating system, tools, editor extensions, and initialization commands, all in a configuration file versioned alongside your code.

When someone clones the repository and opens VS Code, the editor detects the .devcontainer/devcontainer.json file and offers to spin up the environment automatically. Within two minutes they have Node.js, Python, Git, Claude CLI, and every extension installed, exactly like you.

COMPARISON

Without DevContainer vs With DevContainer

WITHOUT DEVCONTAINER

"It works on my machine"

  • Hours of setup for every new team member
  • Differences between dev and production environments
  • "Install version 18, not 20" — messages in Slack
  • The AI doesn't know what tools it has available
  • Painful onboarding every time someone new joins
WITH DEVCONTAINER

Same environment. Always.

  • New person → clones repo → opens VS Code → ready in 2 min
  • Environment identical to production, no surprises
  • All tools preinstalled and versioned
  • The AI knows exactly what the environment is and can leverage it
  • Onboarding that scales without manual effort
FILE ANATOMY

The 5 sections of a devcontainer.json

  • 01

    name — Environment identifier

    "my-project-dev" — Just for identification in VS Code. Descriptive and in English.

  • 02

    image — Container base image

    "mcr.microsoft.com/devcontainers/javascript-node:20" — The official image with Node.js 20 already installed.

  • 03

    features — Additional tools

    git, docker-in-docker, github-cli. Each feature is one line: the container installs them automatically when created.

  • 04

    customizations.vscode.extensions — Editor extensions

    ["ms-azuretools.vscode-docker", "eamodio.gitlens", "usernamehw.errorlens"] — Installed automatically when opened in the container.

  • 05

    postCreateCommand — Initialization command

    "npm install && echo 'Environment ready'" — Runs once, when the container is created for the first time.

REAL CODE · COPY AND USE

devcontainer.json in full

{
  "name": "hello-world-express",
  "image": "mcr.microsoft.com/devcontainers/javascript-node:20",
  "features": {
    "ghcr.io/devcontainers/features/git:1": {},
    "ghcr.io/devcontainers/features/github-cli:1": {}
  },
  "customizations": {
    "vscode": {
      "extensions": [
        "ms-azuretools.vscode-docker",
        "eamodio.gitlens",
        "usernamehw.errorlens"
      ]
    }
  },
  "postCreateCommand": "npm install"
}

image. The official Microsoft image with Node.js 20 LTS. Change the number to pin a different version.

features. Git and GitHub CLI are added on top of the base image. Each feature is an independently versioned module.

extensions. These three extensions are installed automatically for everyone who opens the project in a container.

postCreateCommand. npm install runs once when the container is created. Add any initial setup here.

CHAPTER 02

CLAUDE.md

The onboarding you'd give a new team member. Without it, the AI assumes. With it, the AI knows.

WHAT IS CLAUDE.md

The file that gives your project its identity

Every time you open Claude Code in a project, it reads CLAUDE.md before doing anything. It's your chance to define who you are, what you're building, and how you want it to work.

We're looking at this through Claude Code because it's the most widely used tool in the course, but every agent has its equivalent file. The principle is the same: give it persistent context before it starts working.

THE 5 KEY SECTIONS

Anatomy of an effective CLAUDE.md

  • 01

    Project description

    What it is, who it's for, and what problem it solves. 2-3 paragraphs. It's the first thing the AI reads: the purpose must be clear.

  • 02

    Technology stack

    All the tools, versions, and frameworks. The AI will know exactly what it can use and what not to make up.

  • 03

    Team conventions

    File naming, comment language, preferred folder structure. Automatic consistency in every line generated.

  • 04

    Working rules

    What shouldn't change without asking first. How to handle errors. When to commit. The constraints that save projects.

  • 05

    Business context

    Who the end user is, what the product's goal is, and what's the priority. The AI makes better decisions when it understands the why.

REAL EXAMPLE · TEMPLATE

CLAUDE.md in full

# hello-world-express

Node.js + Express web app that displays "Hello world"
on port 3000, containerized with Docker.

## Stack
- Backend: Node.js 20 + Express 4.x
- Containers: Docker + docker-compose.yml
- Deploy: Vercel (configured in vercel.json)
- AI agent: Claude Code / Antigravity

## Conventions
- Files in English with hyphens (my-file.js)
- Environment variables NEVER hardcoded
- Commits following Conventional Commits (feat:, fix:…)

## Rules
- Before any big change, explain the plan to me first
- Do not modify docker-compose.yml without confirmation
- Make a git commit for every completed feature

Clear description. Two sentences that define what it is. The AI already has the context before reading anything else.

Explicit versions. Express 4.x, Node.js 20 — without versions the AI might use APIs that don't exist in your environment.

Protective rules. "Do not modify docker-compose.yml without confirmation" prevents well-intentioned but destructive changes.

CHAPTER 03

Specialized agents

For complex projects, multiple specialized agents are more effective than one generalist. Divide and conquer.

AGENT ARCHITECTURE

A specialized AI team

Claude Code acts as the orchestrator: it delegates each type of task to the agent that knows it best, each with its own instructions and judgment.

Agents are defined as .md files in .claude/agents/ with instructions specific to that role. Claude Code orchestrates between them depending on the type of task.

An architect agent designs the structure. An implementer agent writes the code. A tester agent verifies that it works. A documentation agent keeps the README up to date. Each one does one thing and does it well.

AGENT DEFINITION · .claude/agents/

Anatomy of a specialized agent

---
name: code-reviewer
description: Reviews generated code looking for bugs,
  security issues, and quality improvements.
---

You are an expert code reviewer.
When you review code:

1. Look for potential bugs before they reach production
2. Identify security issues (SQL injection, XSS, etc.)
3. Suggest readability improvements without changing the logic
4. Verify that CLAUDE.md conventions are being followed
5. If something is good, say so explicitly — don't just point out errors

YAML frontmatter. name and description are the metadata Claude Code uses to decide when to invoke this agent.

Role instructions. The section after the --- defines the personality and behavior. The more specific, the better the result.

Task list. Numbering the responsibilities helps the agent avoid missing a step during long reviews.

CUSTOM SKILLS

Skills: workflows in a single command

Instead of writing the same long prompt every time, you define the skill once and invoke it with /name.

Skills are reusable commands that encapsulate a complete workflow. They're defined in .claude/skills/ as .md files with the process instructions.

/deploy

Verifies tests, deploys to Vercel, and updates the CHANGELOG automatically.

/review

Reviews code pending commit: bugs, security, and CLAUDE.md conventions.

/test-all

Runs the test suite, groups the failures, and proposes fixes.

/document

Updates the README and comments for every file changed since the last commit.

CREATE-SKILL · A SPECIAL SKILL

The skill that creates other skills

There's a special skill: one that helps you discover what skills you need and creates them. Claude installs it in your project when you ask for it.

Once installed, you can ask it to analyze your usual workflow and suggest which processes are worth turning into reusable skills.

The process is simple: you describe the workflow once, and the skill turns it into an invokable command that any team member (or you, in a different context) can use without having to remember the details.

To install it: claude "create a skill called create-skill that helps me discover and create useful skills for this project"

CHAPTER 04

Anatomy of an Effective Prompt

A vague prompt produces vague results. A structured prompt produces precise code.

THE 5 ELEMENTS OF A PROMPT

The 5 blocks of a prompt that works

A vague prompt produces vague results. A structured prompt produces precise, predictable code.

Every effective prompt has five components. You can use all of them or only the ones that apply to your case, but knowing them gives you a mental checklist before you hit send.

IN PRACTICE

Vague Prompt vs Effective Prompt

VAGUE PROMPT

"Add a login to my website."

  • The AI makes assumptions about the stack
  • It might use the wrong library
  • It might create a users table different from the existing one
  • Result: code that needs to be rewritten
  • Time lost: 30-60 minutes of fixes
EFFECTIVE PROMPT

"My website uses Node.js + Express + PostgreSQL. I need email authentication with bcrypt. Don't change the users table. After login it should redirect to /dashboard. Before writing any code, explain the plan to me."

  • Context: Node.js + Express + PostgreSQL
  • Goal: email authentication with bcrypt
  • Constraint: don't change the existing users table
  • Success criteria: redirects to /dashboard
  • Format: file plan before code
PAUSE · REFLECTION

Which prompt element do you forget most often?

We just covered the 5 blocks of an effective prompt. Identify your weak spot.

  • AContext — I don't always explain what's already in the project before asking for something new
  • BConstraints — I forget to tell it what not to touch or change
  • CSuccess criteria — I don't define how I'll know the result is correct
  • DOutput format — I don't specify which files to create or what structure I want
